
# HW-12 — Ответы на эксперименты

## Часть 1. Check-in

### T1 — Первый Check-in

**Проблема:** исходный код возвращал HTTP 200 вместо 201, массив вместо объекта и не содержал полей `ended_at` и `note`.

**Исправление:** использованы `response($timeEntry->toArray(), 201)` и `refresh()` после создания записи.

**Результат:** 201 Created, корректный объект с `ended_at: null`, `note: null`, `is_manual: false`.

### T2 — Повторный Check-in

**Проблема:** повторный запрос создавал вторую открытую рабочую запись.

**Исправление:** добавлена проверка незакрытых записей через `whereNull('ended_at')`.

**Результат:** 409 Conflict — `You are already checked in`.

### T3 — Проверка отпуска

**Проблема:** исходный код не проверял наличие утверждённого отпуска.

**Исправление:** добавлена проверка `leaveRequests()` по статусу `approved` и текущей дате UTC.

**Результаты:**
- `approved` → 409 Conflict, Check-in запрещён.
- `pending` → 201 Created, Check-in разрешён.

### T4 — Проверка UTC

**Проблема:** `date()` зависит от часового пояса PHP.

**Исправление:** для времени начала работы используется `gmdate()`.

**Результат эксперимента:**

```text
date:   2026-11-15 20:05:32
gmdate: 2026-11-15 18:05:32
```

В данном эксперименте разница составляет 2 часа при часовом поясе `Europe/Kyiv`. `gmdate()` возвращает UTC независимо от настройки часового пояса PHP.

## Часть 2. Lunch Start / Lunch End

**L1 — Lunch Start без Check-in:** 409 Conflict — `You are not checked in`.

**L2 — Check-in:** 201 Created — рабочая смена успешно открыта.

**L3 — Lunch Start:** 201 Created — создана запись типа `lunch` с `ended_at: null`.

**L4 — Повторный Lunch Start:** 409 Conflict — `You are already on lunch`.

**L5 — Lunch End:** 200 OK — обед завершён, поле `ended_at` заполнено.

**L6 — Повторный Lunch End:** 409 Conflict — `You are not on lunch`.

**L7 — Второй Lunch Start за день:** 409 Conflict — `Lunch has already been taken today`.

**Результат:** реализованы методы `lunchStart()` и `lunchEnd()`. Проверяются состояние сотрудника, наличие открытого обеда и ограничение на один обед в день. Время сохраняется в UTC.

## Часть 3. Check-out

### O1 — Проверка открытых записей

**Проблема:** `empty($timeEntries)` некорректно проверяет коллекцию Eloquent.

**Исправление:** используется поиск открытой рабочей записи и проверка `if (!$work)`.

**Результат:** первый Check-out возвращает `200 OK`, повторный — `409 Conflict` с сообщением `You are not checked in`.

### O2 — Транзакция

**Проблема:** исходный код использовал транзакцию через `db()` (PDO), а изменения записей выполнялись через Eloquent. Это не гарантировало общий откат.

**Исправление:** используется `Capsule::connection()->transaction()`.

**Результат:** Check-out успешно закрывает рабочую смену. Закрытие открытого обеда в той же транзакции предусмотрено кодом, но отдельный тест одновременного закрытия ещё необходимо подтвердить.

### O3 — Ночная смена

**Проблема:** исходный код искал только записи, начатые сегодня, поэтому не находил открытую ночную смену.

**Исправление:** убран фильтр по дате, используются все незакрытые записи пользователя.

**Результат:** смена, начатая вчера, успешно завершается — `200 OK`. Повторный Check-out возвращает `409 Conflict`.

## Часть 4. Status и Entries

### S1 — Статус сотрудника

**Проблемы:** `worked_minutes` возвращался строкой, учитывалась только первая рабочая запись, `server_time` имел неправильный формат. Также существовал риск обращения к `$lunch->ended_at`, когда обед отсутствовал.

**Исправление:** реализован подсчёт всех рабочих интервалов за день с вычитанием обеда, исправлены `allowed_actions`, сортировка и формат времени UTC.

**Результат:** корректный JSON с числовыми `worked_minutes` и `lunch_minutes`, правильными состоянием и доступными действиями.

### S2 — Расчёт рабочего времени

- Lunch: 08:00–08:30 — 30 минут.
- Work: 11:00–12:00 — 60 минут.

**Результат:** `worked_minutes = 270`, `lunch_minutes = 30`. Тест успешно пройден.

### S3 — Сортировка записей

**Исправление:** добавлена сортировка `orderBy('started_at')`.

**Результат:** записи возвращаются в хронологическом порядке.

### Проверка GET /api/me/entries

Корректный диапазон дат возвращает `200 OK`. При `from > to` возвращается `422 Validation` с сообщением `Must be after or equal to from`.

Исправлена проблема продолжения выполнения после `jsonError()` с помощью `HttpException`.

### Проверка GET /api/time-entries

Администратор получает записи сотрудника — `200 OK`.

Обычный сотрудник получает `403 Forbidden`, запрос без токена — `401 Unauthorized`.

Для несуществующего пользователя возвращается `404 Not Found`. Исправлено продолжение выполнения после ошибки, которое ранее вызывало `TypeError`.

### A2 — Несуществующий пользователь

**Проблема:** при запросе с `user_id=999999` функция `jsonError()` выводила ошибку `404`, но выполнение продолжалось. В результате `getEntries()` получал `null` вместо объекта `User`, что вызывало `TypeError`.

**Исправление:** заменён вызов `jsonError()` на `throw new HttpException(404, 'not_found', 'User not found')`.

**Результат:** при запросе с `user_id=999999` возвращается один JSON-ответ со статусом `404 Not Found` и сообщением `User not found`. Ошибка `TypeError` больше не возникает. Тест успешно пройден.

## Часть 5. Admin Edit

**Endpoint:** `PATCH /api/time-entries/{id}`

Реализовано редактирование записей рабочего времени администратором.

### Результаты тестирования

- Без токена — `401 Unauthorized`.
- С токеном обычного пользователя — `403 Forbidden`.
- Успешное редактирование администратором — `200 OK`, `is_manual: true`.
- Несуществующая запись — `404 Not Found`.
- Неправильный формат даты — `422 Unprocessable Entity`.
- Время окончания раньше времени начала — `422 Unprocessable Entity`.
- Дата начала в будущем — `422 Unprocessable Entity`.
- Пересечение с другой записью того же типа — `409 Conflict`.
- Открытый интервал (`ended_at = null`), пересекающийся с другой записью — `409 Conflict`.
- Обед за пределами рабочего интервала — `409 Conflict`.
- Сокращение рабочего интервала, при котором существующий обед выходит за его пределы — `409 Conflict`.

### Безопасность

При обновлении используются только разрешённые поля: `started_at`, `ended_at`, `note`. Поле `created_by` устанавливается сервером на основании авторизованного администратора.

Переданные клиентом значения `user_id`, `type` и `created_by` не используются для массового обновления.

При проверке пересечений записей одного типа текущая запись исключается по ID. Открытые интервалы (`ended_at = null`) рассматриваются как интервалы без верхней границы.

Дополнительно проверяется, что обед полностью находится внутри рабочего интервала, а изменение рабочего интервала не нарушает границы существующих обедов.

**Итог:** основные сценарии Admin Edit протестированы. Успешное редактирование подтверждено ответом API с `is_manual: true`. Проверку значения `created_by` непосредственно в базе данных необходимо завершить отдельно.
