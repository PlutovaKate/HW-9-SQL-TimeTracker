## Частина 1

### M1. `$user->toArray()` у відповіді логіну
- Прогноз: Если заменить ручное формирование данных пользователя на $user->toArray(), Eloquent вернёт все доступные поля модели, включая password, api_token и token_expired_at, поскольку мы ещё не настроили $hidden. Также в ответе не будет вычисляемого поля role_label.
- Факт (що є в `user`): После замены PDO на Eloquent авторизация работает. Метод $user->toArray() возвращает поля password, api_token и token_expired_at. Поле role_label отсутствует. Поле role возвращается строкой employee, а is_active — логическим значением true.
Дополнительно обнаружено, что ответ содержит двойное вложение data, а значение api_token внутри пользователя отличается от нового токена авторизации.
- Чого там не повинно бути і чому воно там: В модели User пока не настроено свойство $hidden, поэтому Eloquent включает конфиденциальные поля в результат toArray(). Поле role_label отсутствует, потому что для него ещё не создан accessor. Старый api_token остаётся в объекте модели, поскольку обновление токена выполняется напрямую через PDO, без обновления объекта Eloquent.

### M2. Логін без міграції 007 і `create()` інших моделей

**1. Прогноз**

**Логин:** При замене PDO на `$user->update()` ожидаю ошибку SQL, поскольку Eloquent автоматически обновляет поле `updated_at`, которого пока нет в таблице `users`.

**Создание записей:** При вызове `Holiday::create()`, `LeaveRequest::create()` и `TimeEntry::create()` ожидаю ошибки, связанные с отсутствием столбцов `created_at` или `updated_at`.

**2. Факт (логін; кожен з трьох `create()`)**

**Авторизация:**

После замены PDO на `$user->update()` возникла ошибка:

`SQLSTATE[42S22]: Column not found: 1054 Unknown column 'users.updated_at' in 'field list'`

После выполнения миграции `008_add_updated_at_to_users.sql` повторный запрос авторизации через Postman вернул `200 OK`. Токен успешно сохраняется через Eloquent.

**Создание записей:**

| Модель | Первоначальный результат | После исправления |
|---|---|---|
| `Holiday::create()` | Сначала класс не был найден, после исправления имени класса — ошибка `Unknown column 'updated_at'` | `OK` |
| `LeaveRequest::create()` | `Unknown column 'updated_at'` | `OK` |
| `TimeEntry::create()` | `Unknown column 'updated_at'`, затем ошибка преобразования `created_by` в дату | `OK` |

После исправлений все три операции `create()` успешно выполнились в тестовых транзакциях. Изменения были отменены через `rollBack()`.

**3. Чому і як виправив кожну модель**

Причина ошибок — Eloquent по умолчанию автоматически управляет полями `created_at` и `updated_at`, но структура таблиц не везде предусматривает оба столбца.

- **User:** добавлен столбец `updated_at` через SQL-миграцию `008_add_updated_at_to_users.sql`.
- **Holiday:** добавлено `public $timestamps = false;`, поскольку таблица не использует автоматические временные метки.
- **LeaveRequest:** добавлено `const UPDATED_AT = null;`. Автоматическое заполнение `created_at` сохранено, а обновление отсутствующего `updated_at` отключено.
- **TimeEntry:** добавлено `public $timestamps = false;`, поскольку таблица не содержит автоматических временных меток. Дополнительно исправлена неправильная обработка поля `created_by`, которое должно содержать ID пользователя, а не дату.

**Вывод:** При использовании Eloquent необходимо учитывать реальную структуру таблиц. Если столбцы временных меток отсутствуют, нужно отключить их автоматическое заполнение или добавить необходимые столбцы через миграцию.

### M3. N+1
- Прогноз (скільки запитів у кожному варіанті): При использовании LeaveRequest::all() и последующем обращении к $leave->user Eloquent будет выполнять дополнительные SQL-запросы для каждой заявки. С with('user') количество запросов должно уменьшиться.
- Факт: В базе данных 7 заявок на отпуск.
Без with() — 8 SQL-запросов.
С with('user') — 2 SQL-запроса.
- Звідки різниця і скільки буде на 1000 заявок:
Без with() Eloquent сначала выполняет 1 запрос для получения всех заявок, а затем отдельный запрос для получения пользователя каждой заявки. Поэтому для 7 заявок получилось 8 запросов (1 + 7).
С with('user') Eloquent выполняет всего 2 запроса: первый получает все заявки, второй — всех связанных пользователей.
Если будет 1000 заявок:
Без with() — до 1001 SQL-запроса (1 + 1000).
С with('user') — 2 SQL-запроса.
Таким образом, with() решает проблему N+1 и уменьшает нагрузку на базу данных.

### M4. `$fillable`

**Що надішле хитрий користувач у `User::create(requestBody())`:**
Пользователь может отправить дополнительные служебные поля: `role = admin`, `is_active = true`, `api_token = test-token`, `token_expired_at = 2026-12-31 23:59:59`.
Если эти поля присутствуют в `$fillable`, Eloquent разрешит их массовое заполнение. Это потенциальная уязвимость, поскольку пользователь может попытаться изменить свои права доступа или данные авторизации.
**`update(['api_token' => ...])` без `api_token` у `$fillable` — прогноз:**
Предполагаю, что после удаления `api_token` и `token_expired_at` из `$fillable` метод `$user->update([...])` больше не будет сохранять переданные значения, поскольку Eloquent защищает эти поля от массового заполнения.
***Факт (що в БД):**
До исправления `$fillable` метод `User::create()` принимал служебные поля `role`, `is_active`, `api_token` и `token_expired_at`.
После удаления этих полей из `$fillable` массовое заполнение перестало работать.
Отдельно проверила `$user->update(['api_token' => 'test-token-update'])`. Результат: `token_not_changed`, `value_unchanged = true`. После повторного чтения модели значение токена не изменилось.
**Чому і як тепер зберегти токен:**
Метод `update()` использует массовое заполнение и учитывает `$fillable`. Поэтому `api_token` через него больше не обновляется.
Для сохранения токена в `AuthController` использую прямое присваивание свойств:
```php
$user->api_token = $token;
$user->token_expired_at = $tokenExpiredAt;
$user->save();
```
Прямое присваивание не ограничивается `$fillable`, поэтому приложение может сохранить токен после успешной авторизации. Проверка `POST /api/login` вернула `200 OK` и новый токен.


## Частина 2

### A1. Атрибут з `jsonError()` без зупинки
- Прогноз: Если при отсутствии токена вызвать jsonError(401, ...), но не остановить выполнение программы, контроллер может продолжить работу после отправки ошибки. В результате в HTTP-ответе могут оказаться одновременно JSON с ошибкой и данные, которые вывел контроллер. Такой ответ будет некорректным. Предполагаю, что одного return внутри метода атрибута недостаточно, поскольку он завершает только этот метод, а не выполнение Router.
- Факт: (GET /me і POST /auth/logout без токена — тіло і статус):
GET /api/me без токена вернул JSON с ошибкой unauthorized и сообщением Unauthenticated. После JSON в теле ответа появилась ошибка Xdebug: Fatal error: Call to a member function toArray() on null в AuthController.php, строка 54.
POST /api/auth/logout без токена также вернул JSON с ошибкой unauthorized и сообщением Unauthenticated. После JSON появилась ошибка Xdebug: Fatal error: Attempt to assign property "api_token" on null в AuthController.php, строка 64.
Ожидаемый HTTP-статус обоих запросов — 401 Unauthorized (нужно подтвердить в Postman).
- Чому: return в атрибуті не допомагає: return завершает только выполнение метода Auth::__invoke(). После этого управление возвращается в Router::runAction(), который продолжает выполнение и вызывает метод контроллера. Чтобы остановить выполнение, необходимо передать ошибку на уровень Router или выше, например, через исключение HttpException. HTTP-статус обоих запросов — 401 Unauthorized

### A2. `#[\Deprecated]` над `me()`
- Прогноз: Router попытается выполнить #[\Deprecated] как функцию. Поскольку этот атрибут не имеет метода __invoke(), возникнет ошибка.
- Факт: При запросе GET /api/me с действительным токеном возникла ошибка Fatal error: Object of type Deprecated is not callable в Core/Router.php, строка 56. HTTP-статус — 200 ОК.
- Чому і що змінив у runAction(): Router выполнял все атрибуты подряд, не проверяя их назначение. Я изменила только атрибуты, реализующие интерфейс Middleware, с помощью getAttributes(Middleware::class, ReflectionAttribute::IS_INSTANCEOF). Вместо new $attrClass использовать newInstance(), чтобы корректно создавать атрибуты и передавать аргументы их конструкторам.

### A3. Заголовок `authorization` малими літерами
 - Прогноз: Лекционный вариант apiToken() может не найти токен, если заголовок называется authorization маленькими буквами, потому что PHP различает регистр ключей массива.
- Факт: Заполнить после проверки вручную заданного заголовка. С обычным Bearer Token уже получен 200 OK.
- Чому (і що з NotBearer <токен>): По стандарту HTTP имена заголовков не зависят от регистра. Поэтому лучше использовать $_SERVER['HTTP_AUTHORIZATION']. Строгое регулярное выражение /^Bearer\s+(\S+)$/i принимает только правильный формат Bearer. Лекционное выражение /Bearer\s(\S+)/ может ошибочно принять NotBearer <токен>, поскольку ищет Bearer внутри строки.

### A4. Деактивований користувач з живим токеном
- Прогноз: Если деактивировать пользователя, но оставить его токен действительным, доступ должен быть запрещён, поскольку auth() проверяет is_active.
- Факт: Заполнить после проверки в Postman.
- Чому і де тепер перевіряються строк дії та is_active: Проверки находятся в функции auth(). Она ищет пользователя по токену и дополнительно проверяет token_expired_at и is_active. Если хотя бы одно условие не выполняется, возвращается null, а атрибут #[Auth] вызывает исключение HttpException со статусом 401. Для предотвращения повторных SQL-запросов используется static $user.

## Частина 3

### C1. Два логіни поспіль, потім logout
- Прогноз: При первом входе пользователь получит Token A, при втором — Token B. После второго входа первый токен перестанет работать (401), а второй будет действительным (200). После logout второй токен также станет недействительным (401).
- Факт (перший токен; другий після logout):
Первый токен после второго входа → 401 Unauthorized.
Второй токен до logout → 200 OK.
Logout со вторым токеном → 204 No Content.
Второй токен после logout → 401 Unauthorized.
- Чому і що змінити для кількох пристроїв: В таблице users хранится только один api_token. При повторном входе новый токен перезаписывает предыдущий, поэтому первый токен перестаёт работать.
Для поддержки нескольких устройств нужно создать отдельную таблицу api_tokens с полями id, user_id, token, expired_at, device. Тогда каждый вход будет создавать отдельный токен, а logout сможет удалять только токен текущего устройства.

### C2. bcrypt і 72 байти
- Прогноз: Оба результата будут true, поскольку bcrypt учитывает только первые 72 байта пароля и игнорирует остальные.
- Факт (`...aY`; 72 літери `a`):
Пароль из 72 букв a и последней буквы Y → true.
Пароль из 72 букв a → true.
Оба пароля успешно проходят password_verify(), хотя исходный пароль при хешировании содержал 72 буквы a и последнюю букву X.
- Чому, і що з кириличним паролем з 40 літер: bcrypt использует только первые 72 байта пароля.
mb_strlen() считает количество символов, а strlen() — количество байт.
Например, 40 кириллических букв в UTF-8 обычно занимают 80 байт (40 × 2). Поэтому такой пароль может пройти проверку max:72 по количеству символов, но bcrypt проигнорирует байты после 72-го.
Чтобы контролировать ограничение bcrypt, необходимо проверять длину пароля в байтах с помощью strlen().
